## 项目判断

RKV-1 已具备可恢复原文、查历史版本和核验证据来源的底座。接下来的主任务是验证 **资料持续修订时，系统能否回答新问题，给出正确版本中的充分依据，并把使用成本控制在事先约定的范围内**。

- **保留可靠性成果。** 原文身份、历史版本、损坏拒绝和真实进程退出都有各自的验证。v0.99 的协作写锁要求写入方使用对应入口，锁释放与操作完成分别判定。[v0.99 报告](../results/v0.99.0/SUMMARY.md)
- **把局部指标与答案质量分开。** 两批小样本显示检索证据有帮助。24 道有标注的检索题中，8 道缺少标注论文，4 道已有标注论文仍判错。论文命中、原句覆盖、证据充分性和判断正确性分别计量。[失败诊断](../results/v0.88.0/SUMMARY.md)
- **用负结果缩小研究范围。** 已测神经预测压缩候选没有通过完整净收益门槛。结构模板在一次测试中对 532 道题全部拒答。重启这类方向需要新机制假设、独立验证输入和完整成本账本。[压缩路线](ROADMAP.md) · [模板测试](../results/v0.76.0/SUMMARY.md)
- **按使用问题安排工程投入。** 执行观测和故障处理修复了真实缺口。后续工程改动要明确它解除的使用障碍或实验阻塞。公开版本按完整能力组织，单独的诊断可作为研究记录留存。

## 评测与决策规则

1. **设一个功能相当的简单对照。** 普通压缩归档、基础检索和明确的版本记录作为对照，当前 RKV 作为另一组，有充分理由再引入一个候选。同一问题、资料、预算和模型条件保持可比。直接提供标注证据的条件仅用于诊断上限。
2. **分别验收机制和科学质量。** 自建资料用于验证版本、原文、更新和引用身份。科学评测使用独立问题和可信评分，主要看有充分证据的正确回答率，并记录错误确信、拒答和版本错误。按资料或问题家族划分输入，事先定样本量和最低有用改善。重复运行用于观察波动。
3. **算完整成本。** 分列历史投入、部署资源、一次建设和每次使用成本。计入原文、索引、模型、更新、校验和失败成本，共享费用按明确规则分摊。未知项保留未知，应用返回字节、物理读写和峰值内存分别报告。
4. **保留原始分母与结果。** 正式运行前固定代码、协议和输入身份，按适用流程完成独立核验。失败后保留原条件和分母。再次研究应提出新假设并使用独立验证。v0.89 与 v0.95 原轮次保持封存，其未完成情况按各自记录解释。[v0.89 报告](../results/v0.89.0/SUMMARY.md) · [v0.95 观测更正](ROADMAP.md#v095执行可观测性更正)

开工记录用几句话写清 **使用问题、已有证据、本轮只改变的因素、对照和通过条件、成本上限、停止条件**。证据不足时先设计能区分原因的检查。新增外部模型调用或下载须有相应授权。
我的判断是：RKV-1 已经做出了有价值的存储和证据核验底座，但最近的推进明显偏向“把系统做得更可靠”，对“科学问题能否答得更好、更省资源”的验证还不够。接下来应该收拢目标，完成必要的工程整合，然后用一个完整的实际任务检验价值。

打个比方：我们已经把资料室的防丢、目录、版本登记、查阅记录和门锁做得越来越完善；现在最需要证明的是，研究者使用这间资料室，是否真的能更可靠、更高效地完成工作。

下面的反思基于仓库现有结果和私有原型，不是新的实验结论。

首先，哪些工作值得保留，哪些问题需要正视。
方面	已经获得的价值	仍然存在的问题
原文和历史版本	能恢复原始资料、查旧版本、核对来源，部分增量存储有收益	尚未证明在完整成本下普遍优于简单成熟方案
检索和模型回答	两批小样本中，提供检索证据比不给或错配证据更有帮助	新资料、新问题上的稳定收益还没有证明
形式规则与证明	能检查特定规则下的推导和来源	把自然语言正确理解成规则，仍是明显短板
故障与读写协调	对中断、版本混用和协作写入的处理更清楚	这些通过不能折算成问答、推理或长期记忆能力
实验与交付	负结果、未知状态和实际发布包都有记录	版本与报告很多，主要结论反而不容易看清


原始路线要求同时考虑压缩、资源成本和科学推理；目前这几个方向的发展并不均衡。[原始目标与阶段验收 (line 1)](/E:/memorystorage/docs/ROADMAP.md:1)

我认为最重要的反思有五点。
1. 大目标没有被足够早地收敛成一个可验收的使用场景。
   “科学知识、可逆记忆、压缩、推理、长期对话”包含多种不同问题。保存论文成功，不等于模型理解论文；模型答对单题，不等于经历几十次资料修订后仍能答对。
   后续需要先明确一个具体任务。例如：**资料持续修订时，系统能否回答新问题，并给出正确版本中的充分原文依据。**这样才能判断某项改进到底有没有用。
2. 局部指标与用户真正需要的结果之间，还缺少验证。
   找到正确论文、返回正确字节、引用指纹一致，都很重要，但仍可能答错。已有失败诊断中，两批共24道有标注检索题，8题没有取得标注论文，4题已有标注论文却仍判错。这里同时存在检索和回答环节的问题，而且“论文出现了”也不保证给出的内容充分。[失败定位报告 (line 1)](/E:/memorystorage/results/v0.88.0/SUMMARY.md:1)
   因此，下一步不能只追“命中多少论文”，主指标应当更接近：答案正确，并且关键判断有充分、版本正确的证据。
3. 一些负结果已经足够明确，不宜继续靠小修小补维持同一方向。
   神经预测压缩目前没有通过完整净收益验收；结构模板方法在一次测试中的532个问题全部拒答。这些结果没有证明所有神经方法都无效，但足以说明：现有候选不能靠增加证明、优化运行速度或继续堆模板，就自动获得科学价值。[模板泛化结果 (line 1)](/E:/memorystorage/results/v0.76.0/SUMMARY.md:1)
   应当把失败路线封存为知识，只有出现新的机制依据和独立验证条件时再开启。
4. 我的推进方式过于容易围绕下一个局部工程问题展开。
   一个问题被发现后，我倾向于把修复、实验、审计和发行完整做完。这保证了每一轮有交代，却没有足够频繁地追问：这一轮完成后，最初哪个核心目标会更接近验收？
   v0.95之后补执行记录和故障观测有充分理由，但不能让它自然延伸成无限的基础设施建设。今后新增工程工作必须说明：它具体阻挡了哪个核心实验或实际使用场景。
   目前没有完整的人力投入统计，所以不能精确说多少投入被浪费了；但从工作内容判断，推进重心确实需要调整。
5. 状态管理和发布节奏需要收敛。
   README中连续保留多个“当前版本”，状态文件也同时包含历史下一步和较新的停止状态。这会增加误读、重复启动和错误承接的风险。
   应保留完整历史，但让入口只回答三件事：**现在交付了什么、正在准备什么、哪些目标仍未通过。**研究记录可以持续增加，公开版本则按完整能力发布，避免把每个小诊断都变成一次版本升级。
我建议接下来按以下顺序推进。以下是规划，不表示已经启动新实验或模型调用。
顺序	做什么	本阶段交付与结束条件
1．统一目标与现状	建立一份简明能力表，明确已交付、私有准备、未验证；选定一个主要使用场景	每项能力都能指向证据，历史计划不再冒充当前指令
2．完成一次有边界的写入整合	以v0.100私有准备为起点，处理受支持的默认写入、配置变更和命令行入口	真正的独立命令行进程也通过检查；完成兼容、异常和发布验证后结束这条工程线
3．冻结完整任务的评测方案	定义新问题、资料修订、旧版本追问、冲突与缺证据场景；建立简单对照	输入划分、指标、预算、停止规则先确定，再运行正式实验
4．只改最主要的瓶颈	根据对照结果，只选一个有明确机制依据的候选	能说明收益来自哪一环；失败就保留结果，不现场改规则追求通过
5．形成一次完整结论再发布	汇总质量、资源、可靠性和实际安装验证	发布说明能够清楚回答“谁在什么任务上得到什么改善，代价是什么”


第二步需要特别限制范围。现在的写锁需要调用者主动使用，直接调用原来的写入入口仍可绕过；私有v0.100只是原型，命令行验证还依赖注入候选类。下一轮应解决这些明确的使用缺口，但不能顺势宣称解决所有外部工具、恶意修改或断电问题。[当前写入边界 (line 1)](/E:/memorystorage/results/v0.99.0/SUMMARY.md:1) · [私有准备与待办 (line 1)](/E:/memorystorage/.tools/v100-draft/PREPARATION-REPORT.md:1)

第三步是整个规划的中心：做一次真正能够决定方向的对照。

我建议把主场景定为：
一批科学资料经过持续修订后，用户提出此前未用于调参的问题。系统需要回答、引用充分依据，并在需要时准确回到旧版本；证据不足时应明确说明不足。

先把任务分成两层，避免把工程检查和科学能力混在一起：
- **机械层：**检查版本、原文、更新、中断和引用身份，可以使用自建资料。
- **科学层：**检查证据是否充分、答案是否正确，需要独立问题和可信评分；自建机械测试不能替代这一层。
对照至少应包含一个简单且功能相当的方案：普通压缩归档、基础检索、明确的版本记录。再与当前RKV比较，候选改进放在第三组。问题、资料、上下文预算和模型条件保持一致。

这样才能回答：收益到底来自RKV的某项设计，还是任何一个普通检索系统都能取得？

如果将来加入“直接提供标注证据”的条件，它只能用于诊断上限，不能算作实际部署成绩。新模型调用、下载和新数据访问也要单独明确范围，不能沿用已经关闭的实验名额。

评判下一轮时，我会重点看四类数字。
指标	通俗解释
有充分证据的正确回答率	不仅答对，还能拿出支持关键判断的正确版本原文
错误确信与拒答情况	资料不足时是否乱答；也不能靠全部拒答获得好看的安全数字
完整资源成本	保存、建索引、更新、查询、校验和模型调用分别花多少时间、空间与内存
更新后的正确性	资料修订后，新问题是否读对新版本，历史问题是否仍能回到旧版本


样本应按资料或问题家族划分，不能只把同一篇文章的题目随机拆开。重复运行用于观察运行波动，不能当作新增的独立科学题目。具体样本量和最低有用改善，应在正式运行前根据目标和预算确定。

成本也需要更清晰：**历史投入完整保留，但部署成本、一次建设成本和每次使用成本分别报告。**既不能把旧资源当免费，也不能把同一笔共享成本重复相加，制造夸大的总成本。

为了避免再次偏离，我建议增加三条停止规则。
- 一项工程改动如果不能说明它服务于哪个主要任务，就先不做；缓存、Rust优化和更多证明形式都遵守这条规则。
- 候选正式失败后，不在同一批测试题上改预算、阈值或评分补考；再次研究必须有新的假设与合适的独立验证。
- 一个阶段完成后必须产生决策：采用、限定场景保留、封存，或者证据不足。不能只产生“再做一个版本”。
我不建议现在追求“全面突破”或给项目报一个完成百分比。下一轮最有价值的成果，是证明在一个明确的实际场景中，RKV相对简单方案确实改善了结果，而且额外成本值得；如果没有，也能准确知道该停止哪条路线。
